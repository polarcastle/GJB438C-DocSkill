# 句式与表达规范（[20] 软件用户手册适用）

> 生成 `content` 时必须遵守以下规则；写完后逐条自查。

## 1. 操作句式（强制）

- 用户操作一律用"**应**"表述（"用户应……""用户应按……执行"），软件行为用"**软件应……**""软件将……"，不用"必须""要""应该"混用，更不得用"希望""尽量""可能""可以考虑"。
- 每条规程是完整陈述句，主语明确（"用户""软件""调度管理员"等），一条只表达一个动作或要求。
- 操作步骤用"1）2）3）"或"a）b）c）"分级编号逐步书写，每步一个动作，编号层级与模板原有层级一致（如 3.3 的 a）～e）、3.4 b）下的 1）～7））。
- 可选项单独标注"可选选项："；条件分支写明判别条件（"当状态栏显示「已停止」时，……"）。

## 2. 量化要求（强制）

- 性能与容量特性必须给数值＋单位：响应时间（s/ms）、处理时间（s）、容量（条、MB、个）、错误率（%）、平均故障间隔时间（h）、分辨率、字符数上限。
- 资源需求必须给数量与下限：内存（GB）、辅存空间（GB）、设备数量（台）。
- 频率类需求写明周期：备份频率（每日/每周）、归档时间（每日 02:00）、保留时长（保留最近 4 周）。
- 数值范围写"0～99"式闭区间并注明单位；百分比写"不超过 80%"。

## 3. 如实陈述原则（强制）

- 某条确实无内容时，写"无。……不需要/不涉及……"并说明理由，**禁止编造**内容凑数，也禁止留空。
- 无通信设备、无其他设施资源、无批处理等情况，直接如实说明，不得人为区分。
- 消息清单（5.7）只列软件实际会产生的消息，以源码或设计中的消息定义为准；源码无法支撑完整清单时，列出已确认项并标注"待与用户确认"。
- 软件中不存在的菜单、按钮、界面元素不得写入规程。

## 4. 编号与列举格式

- 条内列举用 a）b）c）、1）2）3）、a. b. c. 三级编号，同层编号样式一致；替换模板 a）～e）段落时保留其原编号字母。
- 交叉引用写"见 4.2""见 5.7"，章节号与 JSON 中的 `id` 一致。
- 文档名称用书名号《》，首次出现给出编号和版本（如《示例系统软件需求规格说明》（XT-SRS-V1.0））。

## 5. 禁用表达

- 口语化："东西""搞""大概""差不多""之类的""等等"。
- 营销化："世界领先""极大地""完美"。
- 模糊限定："一般情况下""尽可能""较快"。若确需描述例外条件，写明条件本身（"在……条件下"）。
- 英文缩写首次出现不解释；正文术语与 `references/terminology.md` 不一致。
- 具体单位名称（如高校、公司实名）——全文只写角色定位（"项目承建单位""保障机构"），单位名称由用户在 config.json 中填写。

## 6. 一致性

- 软件名称、缩写、版本号全文一致，且与 `config.json` 封面信息一致（示例系统-任务调度软件 / XT / V1.0）。
- 同一概念全文同一称呼（如统一叫"任务队列"，不得与"任务列表"混用；界面元素名与实际软件一致）。
- 文件名称、消息编号、菜单路径全文一致：xt-scheduler.exe、xt-config.xml、xt-log.db；E-XXXX 错误、W-XXXX 警告、I-XXXX 提示。
- 第 5 章引用的章节号（如"见 3.5""见 5.7"）必须真实存在。
