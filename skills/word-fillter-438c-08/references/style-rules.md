# 句式与表达规范（[08] SRS 适用）

> 生成 `content` 时必须遵守以下规则；写完后逐条自查。

## 1. 需求句式（强制）

- 需求一律用"**应**""**应能**"表述，不用"必须""要""应该"混用，更不得用"希望""尽量""可能""可以考虑"。
- 每条需求是完整陈述句，主语明确（"软件""本软件""编译控制 CSCI"等），一条只表达一个要求。
- 功能行为需求采用"软件应＋动词＋对象＋参数/条件"结构，例如："软件应在 5 s 内完成 10000 行以内源代码的词法分析。"
- 对外部实体接口特性用假设句式："当[未涵盖的实体]这么做时，本软件应该……"，禁止写成"外部系统应……"。

## 2. 量化要求（强制）

- 性能类需求必须给数值＋单位：响应时间（s/ms）、吞吐率（条/s、MB/s）、精度（有效位数）、容量（条、MB）、并发数（个）、利用率（%）。
- 资源使用需求必须给出测量条件（如"处理 10000 行源代码时""连续运行 24 h 时"）。
- 质量因素必须定量（如"错误率不超过 0.1%""平均故障间隔时间 MTBF ≥ 500 h"），不得只写"可靠性高"。
- 数值范围写"0～99"式闭区间并注明单位；百分比写"不超过 80%"，不写"小于 80% 左右"。

## 3. 如实陈述原则（强制）

- 某条确实无内容时，写"本软件无……需求"或"本条不涉及"，**禁止编造**需求凑数，也禁止留空。
- 不需要多种状态和方式、不需要外部接口等情况，直接如实说明，不得人为区分。

## 4. 编号与列举格式

- 条内列举用 a）b）c）、1）2）3）、a. b. c. 三级编号，同层编号样式一致。
- 交叉引用写"见 3.2.1""见表 4-1"，章节号与 JSON 中的 `id` 一致。
- 文档名称用书名号《》，首次出现给出编号和版本。

## 5. 禁用表达

- 口语化："东西""搞""大概""差不多""之类的""等等"。
- 营销化："世界领先""极大地""完美"。
- 模糊限定："一般情况下""尽可能""较快"。若确需描述例外条件，写明条件本身（"在……条件下"）。
- 英文缩写首次出现不解释；正文术语与 `references/terminology.md` 不一致。

## 6. 一致性

- 软件名称、缩写、版本号全文一致，且与 `config.json` 封面信息一致。
- 同一概念全文同一称呼（如统一叫"目标代码"，不得与"目标程序"混用）。
- 第 4、5 章引用的章节号、需求名称必须与第 3 章实际内容一致。
