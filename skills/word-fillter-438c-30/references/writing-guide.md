# [30] 软件安全性设计章节写作要点

> 本文件依据 `GJB438C全套模版/[30]软件安全性设计-438C.doc` 中模板的章节说明文字提炼，逐章给出必写内容、写作深度与常见缺陷。生成任何一章的 `content` 前请先阅读本文件对应小节。

## 本文档的特殊性（先读）

- **[30] 是设计准则类模板**：第 3 章每节的模板文字本身就是安全性设计准则（非"本条应……"式写作指示）。填写时逐条将准则落实为本软件的具体措施或如实陈述不适用，不得整段照抄准则原文充当项目内容。
- **展平结构**：第 3 章在 `project.json` 中为展平 `placeholders` 数组——每个含指导/列举文字的段落对应一项，`id` 为其所属标题的层级编号；同一标题含多个段落时，首段 `id` 即标题编号，其余段落 `id` 为标题编号＋段内序号（从 2 起），如 `3.1.7.2`、`3.13.9.1.25`。修改内容时按 `id` 定位，只改 `content`。
- **第 1 章 1.2/1.3 无指导文字**：模板中"系统概述""文档概述"标题下没有任何待替换段落，引擎不为它们生成规则；项目背景信息写入 `config.json` 的 `content.overview/scope/features`，供生成第 3 章内容时参照。
- **第 2 章无指导段落**：仅含引用文档表，caption「表2-X引用文档」由引擎自动编号为「表2-1引用文档」。
- **第 3 章标题即文档名**："软件安全性设计"在封面两处与第 3 章一级标题共出现 3 次，`document.title` 会被同时写入这三处，因此 `config.json` 的 `document.title` 应固定填「软件安全性设计」。
- **1.1 标识行原文 quirks**：「软件名称；」行原文无冒号（模板排版如此），锚点逐字保留、引擎替换时会自动补冒号；「标题：；」同理带分号。

## 第 1 章 范围

- 1.1 标识：五要素（文档标识号、标题、软件名称、软件缩写、软件版本号）由 `config.json` 的 `document.*` 与 `project.*` 自动填写，校验格式见 `config.json` 中各字段的 `replacement_pattern`。
- 1.2/1.3：模板无指导文字，无填写规则；不要试图在 `project.json` 中为它们加 placeholder（锚点不存在会报"期望命中 1 个段落，实际 0 个"）。
- 常见缺陷：在 project.json 中给 1.2/1.3 编造 replacement_pattern。

## 第 2 章 引用文档

- 用表格列出：序号、名称（含编号）、版本、发布日期、来源。
- 常见缺陷：引用文档与正文实际引用脱节（正文引用了 GJB 900、GJB 2255，表中必须有）；来源栏写"网络"等不可核查字样。

## 第 3 章 软件安全性设计（全文核心）

### 3.1 软件系统设计
- 必写：软硬件功能分配权衡结论；人工确认流程；安全性内核机制；故障自动记录；不回避不安全状态；保密性（防越权存取）设计；安全关键软件标识清单（逐条给出归属）。
- 常见缺陷：只写"按准则执行"不落到模块；安全关键软件清单为空或与实际模块不符。

### 3.2 硬件设计
- 必写：软件与硬件运行过程如何相互交错、相互影响；软件安全性设计对硬件设计的配合要求（上电、复位、看门狗、急停、滤波）；软硬件职责边界。
- 纯软件项目：如实写明与硬件的耦合点（如仅通过标准接口交互），不得编造硬件机制。

### 3.3 软件需求分析
- 必写：不期望事件清单（具体、可核查）、各事件原因分析、对应软件处理要求，三者一一对应。
- 常见缺陷：不期望事件写得笼统（"各种错误"）；原因与措施脱节。

### 3.4 软件危险分析
- 必写：按 GJB 900 在哪些阶段开展危险分析、分析对象与输出物、追踪方式。

### 3.5 安全关键功能的设计
- 逐条响应 a～e：双独立功能控制、模块隔离、强数据类型与多比特编码、计时功能受控、启动前自检测与硬件安全子系统转移。
- 常见缺陷：漏答其中一条；"两位独立"写成"两个变量"式虚假独立。

### 3.6 冗余设计
- 3.6.1 软件冗余：按安全关键等级给出失效容限与冗余要求（几版本、表决方式）；N版本写版本数、相异策略（强制相异/随机相异）、表决规则（含一票否决的适用对象）；恢复块写构成与工作流程。
- 3.6.2 信息冗余：逐条响应 a～d（多源确认、多存储区表决、PROM 备份、RAM 三取二）。
- 常见缺陷：C/D 级软件也写 N 版本（准则明确不考虑失效容限）；表决方式与关键程度不匹配。

### 3.7 接口设计
- 3.7.1 硬件接口要求 / 3.7.2 硬件接口的软件设计：通道检测、非单寄存器/单端口/单命令、行动前极限与合理性检测、校验和与奇偶校验、专用 I/O 端口。
- 3.7.3 人机界面设计：单一行为退出不安全状态、双人"与"方式启动与防误触发、显示无二义性。
- 3.7.4 报警设计：声光报警超背景噪声、例行报警与安全关键报警的区别、未纠正不可清除。
- 3.7.5 软件接口设计：引言＋a～l 参数/变元一致性准则逐条响应。
- 常见缺陷：双人"与"方式只写"需要两人"不写防强迫措施；a～l 准则只答一部分。

### 3.8 软件健壮性设计
- 3.8.1 配合硬件的七个方面（电源失效防护、加电检测、电磁干扰、系统不稳定、接口故障、干扰信号、错误操作）逐节落实。
- 3.8.2 监控定时器：独立时钟源/独立硬件、定时参数的设计依据（受干扰后最小值＞重初始化时间、最大值＜最长故障处理时间）、超时处理。
- 3.8.3 异常保护：异常清单＋保护措施，保护措施必须使系统转入安全状态并保持软件运行。
- 常见缺陷：看门狗写成软件定时器；异常保护只写"打印日志"。

### 3.9 简化设计
- 单入口单出口、模块独立性四准则、扇入扇出（扇出≤7）、耦合五类与内聚六类的优选顺序、复用考虑。
- 量化承诺值给出本项目实际指标（如实际最大扇出）。

### 3.10 余量设计
- 存储量、吞吐能力、处理时间的余量要求；各周期的确定方法与余量保障措施；余量数值必须量化并注明条件。

### 3.11 数据要求
- 数据定义与数据字典、属性控制（值域/变化率）、数值运算范围、精度（有效位）、合理性检查点；协处理器问题按需说明或如实陈述不适用。

### 3.12 防错程序设计
- 参数化、公共变量、标志（含使用说明五项＋安全关键标志唯一性）、文件、非授权存取限制、无意跳转处理、检测点设置、寻址模式、数据区隔离、安全关键信息 a～e（码距、独特位模式、差错检测返回）、信息存储（ROM/EEPROM/EPROM 限制）、算法选择。
- 常见缺陷：安全关键信息用一位逻辑表示（违反准则）；检测点设置无"宜少不宜多"的权衡。

### 3.13 编程要求
- 语言限制、McCabe 指数＜10、单元规模≤200 行、命名、格式、注释（模块头九项、模块内四类、安全关键内容）、程序设计风格四组准则。
- 本项目不用的语言（如 FORTRAN）如实说明并保留准则引用。

### 3.14 多余物的处理
- 未记载特征清除、程序多余物清除、未使用内存初始化（模式必须使系统恢复安全状态，禁随机数/暂停/等待指令）、覆盖处理。

### 3.15 软件更改要求
- 逐条响应 a～d：配置管理与回归测试、禁止目标码修补、现场软件整部件发布、固件更改流程（双人、全功能电路板）。

## 从素材到章节的映射

素材收集阶段形成的「项目画像」（开发语言、模块划分、入口、对外接口/API、关键类与函数、依赖关系）是各章内容的事实来源：

| 本章章节 | 从素材提取的信息 |
|----------|------------------|
| 3.1～3.2 系统/硬件设计 | 部署形态（嵌入式/纯软件）、硬件接口、启动流程、权限与保密需求 |
| 3.3～3.4 需求分析与危险分析 | 项目文档（SRS/建设方案）中的功能与危险源清单、历史故障记录 |
| 3.5～3.8 安全关键功能/冗余/接口/健壮性 | 代码中的看门狗、超时、校验、报警、容错相关模块与配置 |
| 3.9～3.13 简化/余量/数据/防错/编程 | 代码结构（模块规模、扇入扇出、圈复杂度可测项）、编码规范、命名与注释实况 |
| 3.14～3.15 多余物/更改 | 构建配置（未使用代码清理）、配置管理流程、交付形态 |

提取规则：模块名、接口名、函数名一律沿用代码中的命名；素材无法支撑的章节，提示用户补充信息或如实从简；数值类指标必须有素材依据，确实没有时标注"待与用户确认"，不得凭空给数。
