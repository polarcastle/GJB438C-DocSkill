# 句式与表达规范（[22] 测试问题报告适用）

> 生成 `content`、表格 `rows` 以及问题单文字时必须遵守以下规则；写完后逐条自查。

## 1. 如实陈述原则（强制，最高优先）

- 问题报告记录的是**测试事实**：只写实际测试中发现的问题，**禁止编造**未执行过的测试、未发现的问题或虚假的统计数字。
- 第 5 章统计表的每一个计数都必须能在第 4 章的问题报告单（或测试记录）中找到对应的问题；总数必须等于各类分项之和。
- 确实无问题可记时，统计表填 0 并在第 6 章如实说明，不得留空、不得编造 1～2 个"示例问题"充数。
- 源码/测试记录无法支撑的内容，提示用户补充或如实从简，不得虚构。

## 2. 量化与确定性表述

- 计数必须给确定整数（"共发现问题 4 个"），不写"若干""几个""大约"。
- 每个问题必须同时给出：问题类型（四选一）、问题等级（四选一）、问题状态（五选一），分类口径必须与第 3 章模板定义严格一致。
- 描述问题现象时写明触发条件与期望/实际行为："在……条件下执行……时，软件……，期望……，实际……"。

## 3. 编号与列举格式

- 交叉引用写"见 3.2""见表 2-1"，章节号与 JSON 中的 `id` 一致。
- 文档名称用书名号《》，首次出现给出编号和版本。
- 表格单元格内容简洁，不写整段文字；问题详细描述放问题单"问题详细描述"栏（可另加附页）。

## 4. 禁用表达

- 口语化："东西""搞""大概""差不多""之类的""等等"。
- 营销化/评价化："世界领先""极大地""完美""质量不错"。
- 模糊限定："一般情况下""尽可能""较快"。若确需描述例外条件，写明条件本身（"在……条件下"）。
- 对问题原因下无依据的结论：测试报告只记录现象与判定，原因分析属研制方修改记录，不得越权代写。

## 5. 一致性

- 软件名称、缩写、版本号全文一致，且与 `config.json` 封面信息一致。
- 同一问题在问题单、统计表中的类型/等级/状态口径一致（如统一叫"功能错误"，不得与"功能缺陷"混用）。
- 测评依据表中列出的文档编号、版本与被实际引用的文档一致。
