# 句式与表达规范（[07] 安全性大纲适用）

> 生成 `content` 时必须遵守以下规则；写完后逐条自查。

## 1. 大纲句式（强制）

- 计划性、规定性表述一律用"**应**""**应进行**""**应建立**""**应写明**"，不用"必须""要""应该"混用，更不得用"希望""尽量""可能""可以考虑"。
- 每项活动是完整陈述句，主语明确（"本软件""本大纲""项目组"等），一条只表达一项工作或一个要求。
- 活动安排采用"在……阶段，进行……，提出/明确/验证……"结构，例如："在概要设计阶段，进行软件安全性目标分配，将安全性需求落实到各软件部件。"
- 对责任分工用陈述句式："大纲的实施由主管机构和软件开发项目各层次安全负责人分工负责。"

## 2. 量化要求（强制）

- 周期、进度类给出数值＋单位：研制周期（月）、阶段里程碑（日期）、任务完成率（%）。
- 经费类给出数值与口径："约占研制经费的 5%"。
- 度量类指标给出测量条件（如"处理 1000 个周期任务时""连续运行 24 h 时"）。
- 数值范围写"0～99"式闭区间并注明单位；百分比写"不超过 80%"，不写"小于 80% 左右"。
- 无量化依据的数值标注"待与用户确认"，禁止凭空给数（见 SKILL.md「内容生成规范」收尾汇总）。

## 3. 如实陈述原则（强制）

- 某阶段或某项活动确实无内容时，写"本阶段执行模板规定的通用要求"或"本软件无……"，**禁止编造**项目没有的活动凑数，也禁止留空。
- 不需要单独制定的规范、不需要特殊保障措施等情况，直接如实说明，不得人为拔高。
- 模板 4.2.6 评审检查单等标准条款为行业通用要求，如实沿用，不得改写或删除。

## 4. 编号与列举格式

- 条内列举用 a）b）c）、1）2）3）、a. b. c. 三级编号，同层编号样式一致；替换列表项内容时保留原有编号句读（"；"结尾）。
- 交叉引用写"见 3.1""见 4.2.5"，章节号与 JSON 中的 `id` 一致。
- 文档名称用书名号《》，首次出现给出编号和版本。
- 阶段名称用顿号分隔或"——"引出（沿用 3.1 各子条"阶段名——工作内容"格式）。

## 5. 禁用表达

- 口语化："东西""搞""大概""差不多""之类的""等等"。
- 营销化："世界领先""极大地""完美"。
- 模糊限定："一般情况下""尽可能""较快"。若确需描述例外条件，写明条件本身（"在……条件下"）。
- 英文缩写首次出现不解释；正文术语与 `references/terminology.md` 不一致。

## 6. 一致性

- 软件名称、缩写、版本号全文一致，且与 `config.json` 封面信息一致。
- 同一概念全文同一称呼（如统一叫"安全性目标分配"，不得与"安全目标分解"混用）。
- 第 3 章各阶段安排与第 4 章活动项目相互呼应，不矛盾、不重复。
