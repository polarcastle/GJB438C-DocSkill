# [08] 软件需求规格说明（SRS）章节写作要点

> 本文件依据 `GJB438C全套模版/[08]软件需求规格说明-438C.doc` 中模板的章节说明文字提炼，逐章给出必写内容、写作深度与常见缺陷。生成任何一章的 `content` 前请先阅读本文件对应小节。

## 第 1 章 范围

### 1.1 标识
- 必写五要素，逐项列出：a）文档标识号；b）标题；c）软件名称；d）软件缩写；e）软件版本号。
- 标识号格式示例：`TN/x-DO-DS-V{N.xx}`；版本号须与封面"版次"一致。
- 常见缺陷：漏写软件缩写或发布号；标识号与文档封面、页眉不一致。

### 1.2 系统概述
- 必写内容：软件用途；一般特性；开发、运行和维护的历史；需方、用户、开发方和保障机构；当前和计划的运行现场；其他有关文档。
- 写作深度：概述层面，2～3 段，不展开具体功能细节（细节属第 3 章）。
- 常见缺陷：把功能清单搬进来与 3.2 重复；缺少相关方和运行现场；不写维护历史。

### 1.3 文档概述
- 必写：本文档的用途和内容概要；使用本文档的保密性要求（如"内部使用，不得外传"）。
- 常见缺陷：只写"本文档描述了……"一句，漏掉保密性要求。

## 第 2 章 引用文档

- 用表格列出：序号、名称（含编号）、版本、发布日期、来源（编写单位）。
- 须标识不能通过正常采购活动得到的文档的来源。
- 常见缺陷：引用文档与正文实际引用脱节；标准名称不带编号；来源栏写"网络"等不可核查字样。

## 第 3 章 需求（全文核心）

### 3.1 要求的状态和方式
- 若软件在多种状态/方式下运行且需求不同（如空闲、就绪、活动、降级、紧急情况、战时/平时），须标识并定义每一种，并使每个需求与状态/方式对应（可用表格指明）。
- **如实陈述原则**：不需要多种状态和方式时，直接写"本软件在单一状态下运行，不需要区分多种状态或方式"，**不得人为编造区分**。
- **机制约束与折中写法**：填充引擎对 3.1/3.2/3.3/3.4 强制要求 `subsections` 非空（空则报错"动态章节 X 缺少 subsections"），与本条的如实陈述原则存在张力。当软件确为单一状态时，**禁止编造"维护状态""调试状态"等多个子条凑数**；推荐折中——只建一个子条（如 `3.1.1`），子条 `name` 如实描述（如"正常运行状态"），子条 `content` 首句写明"本软件仅有单一运行状态，不区分多种状态或方式"，随后陈述该状态下软件应满足的行为。

### 3.2 软件能力需求
- "能力"是一组相关需求，可按功能、主题、对象划分，每个能力一个子条（3.2.X）。
- 每条能力需求必写：软件行为描述；适用参数——响应时间、吞吐时间、时限约束、时序、精度、容量、优先级别、连续运行需求、基本运行条件下允许的偏差。
- 适当时候必须写：异常条件、非许可条件、超限条件下的行为；错误处理需求；紧急时刻运行连续性的规定。
- 输入/输出相关需求要考虑 3.3.X 列出的主题（数据元素、组合体等）。
- 常见缺陷：只有功能描述没有任何量化参数；没有异常/错误处理需求；子能力未分条。
- 子条 `name` 即生成的章节标题（引擎按 `name`/`content` 直接生成三级标题与正文），必须与代码中的实际模块名一致、以中文开头；量化指标无源码依据时标注"待与用户确认"，不得编造。

### 3.3 软件外部接口需求
- 先写"接口标识和接口图"：每个接口给项目唯一的标识符；用名称、编号、版本、引用文档指明接口实体（系统、配置项、用户等）；声明哪些实体接口特性固定、哪些在开发中；用一张或多张接口图描述。
- 每个接口（3.3.X）按需覆盖以下特性（a～g），从接口实体角度说明差异：
  - a）接口优先级；b）接口类型（实时数据传送、存储检索等）；
  - c）数据元素特征（9 项：名称/标识符、数据类型、大小和格式、计量单位、取值范围或枚举、准确性和精度、优先级/定时/频率/容量/序列等约束、保密性约束、来源和接收者）；
  - d）数据元素组合体特征（记录/消息/文件/数组/显示/报表：8 项，含视听特性）；
  - e）通信方法特征（链接/带宽/频率/介质、消息格式、流控制、传送速率、路由寻址命名约定、传输服务、安全保密考虑）；
  - f）协议特征（优先级别/层次、打包、合法性检查/错误控制/恢复、同步、状态标识报告）；
  - g）其他特征（物理兼容性、电压等）。
- **关键句式**：接口实体的特性若不由本软件决定，应作为假设陈述，用"当[未涵盖的实体]这么做时，本软件应该……"表述，不得写成对其他实体的需求。
- 可引用 RS（接口需求规格说明）、数据字典、协议标准等代替详述。
- 常见缺陷：接口无项目唯一标识符；数据元素缺单位和取值范围；把对外部系统的要求写成"外部系统应……"。
- 接口子条 `name` 即生成的章节标题，须含项目唯一的接口标识符（如"REST 客户端接口（IF-UI-01）"），以中文开头。

### 3.4 软件内部接口需求
- 描述施加于软件内部接口的需求；若全部留待设计时描述，如实陈述。

### 3.5 软件内部数据需求
- 描述对内部数据（数据库、数据文件）的需求；若留待设计决定，如实陈述；若施加需求，按 3.3.X c）d）的主题列出。

### 3.6 适应性需求
- 与安装有关的数据（如场地经纬度、赋税代码）；可随运行需要改变的运行参数。

### 3.7 安全性需求
- 防止或尽可能降低对人员、财产和物理环境的意外危险：既防**意外动作**（如误发"自动导航关闭"），也防**无动作**（如命令发出失败）。
- 涉核部件时写预防意外爆炸、符合核安全规则的需求。
- 每条措施对应一类危险，给出可验证的判据。

### 3.8 保密性需求
- 按需覆盖：保密性环境；保密性类型和级别；须经受的保密性风险；减少风险的安全措施；须遵循的保密性政策；软件须具备的保密性责任；保密性认证/认可准则。无则如实陈述。

### 3.9 软件环境需求
- 运行环境：计算机硬件和操作系统（其他资源需求归 3.10）。

### 3.10 计算机资源需求
- 3.10.1 硬件需求：各类设备数量；处理机、存储器、输入/输出设备、辅助存储器、通信/网络设备的类型、大小、容量等特征。
- 3.10.2 硬件资源使用需求：最大允许的处理机能力、内存容量、I/O 能力、辅存容量、通信/网络能力；给出测量资源使用时所处的条件。
- 3.10.3 软件需求：必须使用的操作系统、数据库管理系统、通信/网络软件、实用软件等，逐项列正确名称、版本和参考文档。
- 3.10.4 通信需求：地理位置、网络拓扑、传输技术、数据传送速率、网关、使用时间、数据类型和容量、时间限制、数据量峰值、诊断特性。

### 3.11 软件质量因素
- 合同或软件研制任务书规定的、或由高一级规格说明派生的质量因素，给**定量**要求：功能性、可靠性、易用性、效率、维护性、可移植性等。

### 3.12 设计和实现约束
- 可引用商用/军用标准；典型：指定体系结构或部件（含数据库）；使用标准或现有部件；使用政府/需方提供的资源；特定设计/实现标准、数据标准、编程语言；灵活性、可扩展性要求。

### 3.13 人员需求
- 使用/支持人员数量、技术水平、责任期限；并发用户数；嵌入帮助和培训；人素工程需求（正常和极端条件下可预见的人为错误；出错消息的颜色和持续时间；关键指示器/按钮位置；听觉信号）。

### 3.14 培训需求 / 3.15 软件保障需求 / 3.16 其他需求
- 培训：与培训有关的软件需求。保障：系统维护、软件保障、运输方式、补给系统、对现有设施和设备的影响。其他：上述未覆盖的需求。均无则如实陈述。

### 3.17 验收、交付和包装需求
- 交付包装、加标记和处理的需求（如以 8 道磁带提交及其包装标签方式），可引用适当标准。

### 3.18 需求的优先顺序和关键程度
- 说明需求的优先级、关键程度或权值；指明对安全性/保密性至关重要的需求以作特殊处理；全部同等重要时如实陈述。

## 第 4 章 合格性规定

- 为第 3 章**每个需求**指定合格性方法和级别，用表格表述。
- 合格性方法（单选）：A-演示（直接可观察的功能操作，无需复杂专用测试设备）；B-测试；C-分析；D-检查（对编码、文档直观检查）；E-特殊方法（专用工具、技术、过程、设施、验收限制）。
- 合格性级别：a-配置项；b-系统集成；c-系统；d-系统安装。
- 含未确认量化指标的需求（源码无依据、标注"待与用户确认"的性能/容量项）：指标未定但行为可验证时，合格性方法优先选 **B-测试**（以测试用例验证行为正确性），与用户确认指标后再补充阈值判据；确实无法测试时选 C-分析。单人/离线无法确认时，保留"待定"标注并在汇总清单中列出（见 SKILL.md「内容生成规范」收尾步骤），不得编造数值后按已定指标选取方法。
- 常见缺陷：方法与需求明显不匹配（如界面显示需求选"分析"）；遗漏关键需求行。

## 第 5 章 需求可追踪性

- 正向追踪：来源指标（如课题可行性研究报告）→ 本文档需求（名称+章节号）。
- 逆向追踪：本文档需求 → 来源指标。
- 存在一对多关系时必须逐条展开，不得以"见第 3 章"笼统代替。
- 章节号必须真实存在，与第 3 章编号一致。
- **已知限制（表头占位符）**：追踪表表头「《XXX课题可行性研究报告》中的指标」是模板 docx 的固定文本，不在可编辑范围（`locator_rows` 机制只保护表头定位、不允许改表头文字），生成文档中该表头会原样保留。当需求来源不是课题可行性研究报告时（例如仅有项目源码与仓库文档），应在本章引言（第 5 章 `content`）中注明实际来源，例如"本章追踪关系依据项目源码与仓库文档（README.md/AGENTS.md）建立"，并在来源列填写真实文档名与小节标题，使表头占位符与正文说明形成对照、不产生事实性误导。

## 第 6 章 注释

- 有助于理解文档的信息：背景、术语、缩略语、公式。无特殊说明也要给出术语和缩略语表。

## 从源码到章节的映射

素材收集阶段形成的「项目画像」（开发语言、模块划分、入口、对外接口/API、关键类与函数、依赖关系）是各章内容的事实来源，按下表从用户项目源码中提取：

| 本章章节 | 从源码提取的信息 |
|----------|------------------|
| 1.2 系统概述 | 软件用途与场景：README/项目说明、入口文件职责、依赖清单反映的定位 |
| 3.2 软件能力需求 | 按代码的功能模块/包划分能力子条；功能描述取自模块职责，输入/输出来自函数签名与返回值，性能参数取自代码中的限制值、配置项和批量规模 |
| 3.3 软件外部接口需求 | 对外 API 路由/函数签名、请求与响应的数据结构、通信协议与数据格式 |
| 3.4 内部接口 / 3.5 内部数据 | 模块间调用与 import/依赖关系、共享数据结构、数据库表/数据文件定义 |
| 3.6 适应性需求 | 配置文件、环境变量、启动参数等运行期可变项 |
| 3.9～3.10 环境与资源 | 依赖清单（pom.xml、package.json 等）、构建与部署配置、容器/脚本中的资源设定 |
| 3.12 设计和实现约束 | 语言版本、框架选型、编码规范、强制依赖 |
| 3.13～3.17 人员/培训/保障/验收 | 部署脚本、运维配置、交付物清单（源码无法支撑时提示用户补充或如实从简） |
| 第 4 章合格性规定 / 第 5 章可追踪性 | 不直接取自源码：方法与级别按各需求的验证可行性选取，章节号引用第 3 章实际编号 |

提取规则：模块名、接口名、函数名一律沿用代码中的命名；代码中不存在的能力、接口、参数不得写入；数值类指标必须有代码或配置中的依据，确实没有时标注为待与用户确认，不得凭空给数。
