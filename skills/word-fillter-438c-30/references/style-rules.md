# 句式与表达规范（[30] 软件安全性设计适用）

> 生成 `content` 时必须遵守以下规则；写完后逐条自查。

## 1. 设计准则句式（强制）

- 设计措施一律用"**应**""**应能**"表述，不用"必须""要""应该"混用，更不得用"希望""尽量""可能""可以考虑"。
- 每条措施是完整陈述句，主语明确（"本软件""任务调度软件""安全监控模块"等），一条只表达一个措施。
- 措施描述采用"主语＋应＋动词＋对象＋条件/参数"结构，例如："安全监控模块应持续监视任务运行状态，检测到不安全状态时应在 100 ms 内将系统转移到安全状态。"
- 对硬件、操作员等外部实体的配合要求，写明软硬件职责边界："硬件负责……，软件负责……"，不得写成对硬件的需求命令。

## 2. 量化要求（强制）

- 时延、周期、容限类指标必须给数值＋单位：响应时间（ms/s）、周期（ms）、余量（%）、圈复杂度（无量纲）、代码规模（行）。
- 资源使用指标必须给出测量条件（如"调度 32 个周期任务时""连续运行 24 h 时"）。
- 不得只写"足够""较快""较大"：余量写"不低于 20%"，时序写"周期为 10 ms"式确定值。
- 数值范围写"0～99"式闭区间并注明单位；百分比写"不超过 80%""不低于 20%"。

## 3. 如实陈述原则（强制）

- 本项目不适用的准则（如纯软件项目不涉及 CPU 间通讯、未使用协处理器、不涉及 FORTRAN），写"本软件不涉及……"或"本条不适用"并说明原因，**禁止编造**硬件配置或机制凑数，也禁止留空。
- 列举型准则（耦合/内聚优选顺序、程序设计风格清单）逐条响应：本项目遵循的写明承诺，不遵循的说明替代措施。

## 4. 编号与列举格式

- 模板原文的列举序号（a. b. c. / a. b. c. / B. / W.）在 content 中**逐条保留原序号样式**，与上下文序号衔接一致。
- 交叉引用写"见 3.8.2""见 3.12.10"，章节号与 JSON 中的 `id` 一致（注意：同一标题含多个段落时，后续段落 id 带段内序号，如 3.1.7.2）。
- 文档名称用书名号《》，首次出现给出编号和版本。
- 段首缩进保持模板风格：content 以 4 个空格开头（与模板指导文字一致）。

## 5. 禁用表达

- 口语化："东西""搞""大概""差不多""之类的""等等"。
- 营销化："世界领先""极大地""完美"。
- 模糊限定："一般情况下""尽可能""较快"。若确需描述例外条件，写明条件本身（"在……条件下"）。
- 英文缩写首次出现不解释；正文术语与 `references/terminology.md` 不一致。

## 6. 一致性

- 软件名称、缩写、版本号全文一致，且与 `config.json` 封面信息一致。
- 同一概念全文同一称呼（如统一叫"安全监控模块"，不得与"安全监控单元"混用）。
- 第 3 章各节引用的模块名、接口名必须真实存在于源码或项目素材中；多处引用的同一机制（如看门狗）全文描述一致。
