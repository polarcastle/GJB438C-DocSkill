# 何时使用

当用户需要基于 `[16]软件测试说明-438C.docx` 模板生成或修改 GJB 438C 软件测试说明（STD）时使用本 Skill。

# 约束

- 只处理 `.docx` 模板，不处理 `.doc`
- 严格模式运行，不做兜底和回退；模板锚点不匹配时必须报错
- 目录通过 Word 域刷新，不直接改目录文本
- 只修改 `content` 字段，不得修改模板结构（锚点 `replacement_pattern`、章节编号等）

# 目录结构

- `documents/[16]软件测试说明-438C.docx`：模板文档
- `templates/config.json`：封面与标识配置
- `templates/project.json`：章节内容（含 3.X/4.X.Y 原型标题改名与逐段填写规则）
- `references/writing-guide.md`：章节级写作要点（必写内容、写作深度、常见缺陷）
- `references/terminology.md`：军用软件术语表（CSCI、STD、STP、测试用例、评价准则等）
- `references/style-rules.md`：句式与表达规范（测试描述句式、量化判据、禁用表达）
- `scripts/main.py`：命令行入口（推荐）
- `scripts/process.py`：免参数入口（不推荐：需将 config/project 拷入 scripts/，会污染技能仓库）

# 工作流

0. **素材收集**：生成任何内容前，先收集并核实输入素材，作为全部章节内容的事实依据：
   - 扫描用户指定的项目源码目录，形成「项目画像」：识别开发语言、模块划分、入口文件、对外接口/API、关键类与函数、依赖关系；
   - 收集测试依据文档（SRS/STP）：用 python-docx 读取，提取需求标识（R-XX）、章节号、被测功能点；**没有 SRS 时，所有需求标识、章节号须与用户确认，禁止编造**；
   - 若用户提供了建设方案文档（.docx 用 python-docx 读取，.md/.txt 直接读取），提取其中的项目背景、建设目标作为补充素材；
   - 写入规则：测试项划分、用例设计、预期结果必须与源码事实和需求文档一致，禁止编造源码中不存在的内容；源码无法支撑的章节，提示用户补充信息或如实从简。
1. 修改 `templates/config.json` 中各字段的 `content`，填写项目名称、版本、单位、日期等封面信息。
2. 修改 `templates/project.json` 中各章节内容：
   - 第 1 章（范围）：1.1 标识概括段、1.2 系统概述、1.3 文档概述
   - 第 2 章（引用文档）：正文逐条列出（**本模板无引用文档表格**）
   - 第 3 章（测试准备）：`3.1` 等原型标题改名（**保留编号、只改名称**）＋硬件/软件/其他准备各段
   - 第 4 章（测试说明）：`4.1`、`4.1.1` 等原型标题改名 ＋ 测试用例七子条（涉及的需求/先决条件/测试输入/预期结果/评价准则/测试规程/假设和约束）逐段填写
   - 第 5 章（需求的可追踪性）：引言＋a) 正向、b) 逆向两条
   - 第 6 章（注释）：术语与缩略语
3. 运行生成脚本（见"运行"章节）。
4. 检查输出 `.docx` 文件，首次在 Word 中打开时刷新目录。

# 内容生成规范

生成每章 `content` 时，必须按以下流程执行：

1. **先读知识库**：生成前阅读 `references/` 下三个文件——
   - `writing-guide.md`：本章必写内容、写作深度与常见缺陷；
   - `terminology.md`：术语的中文全称、英文缩写与使用场景，全文术语与其保持一致；
   - `style-rules.md`：测试描述句式、量化判据、如实陈述原则与禁用表达。
2. **按提示生成**：各字段的 `generation_prompt` 已给出角色定位、要点清单、句式要求和篇幅建议，以其为准并结合工作流第 0 步素材收集得到的项目画像与测试依据文档生成内容。
3. **写后自查**：内容写入 JSON 前，对照 `writing-guide.md` 的要点清单逐条自查——用例七子条是否齐全、评价准则是否量化、预期结果是否可判定、需求标识/章节号/用例号是否真实且在第 4/5 章间闭环、测试步骤是否与软件实际交互方式一致。
4. **再写入**：自查通过后写入 `content`，保持 JSON 结构不变。
5. **收尾汇总（全部 JSON 填写完成后、运行脚本前）**：汇总本文档中所有标注"待与用户确认/待定"的事项，在对话中集中呈现给用户——每项给出所在章节、缺失的信息与建议默认值，请用户逐项确认或接受默认值后再生成；单人/离线无法确认时，保留"待定"标注并原样列入清单，不得自行编造数值补齐。

# JSON 规则

## config.json

config.json 包含 `project`、`document`、`content` 三部分，所有字段只修改 `content` 值。

> **单位名称无默认值**：`project.company` 与 `project.department` 的 `content` 出厂为空，必须由用户明确提供后填写；禁止沿用任何示例单位名或编造。单位名称缺失时引擎会以"字段为空"报错，这是预期行为。

| 字段位置 | type | 说明 | content 生成方式 |
|----------|------|------|-----------------|
| project.* | `original_text` | 项目基础信息（名称、版本、单位等） | 直接使用用户输入 |
| document.* | `original_text` | 文档元信息（编号、标题、日期等） | 直接使用用户输入 |
| content.overview | `background_information` | 项目概述 | 结合用户描述生成 |
| content.scope | `background_information` | 测试覆盖范围 | 结合用户描述生成 |
| content.features | `background_information` | 被测功能特性 | 结合用户描述生成 |

## project.json

### 通用规则

- 所有章节只修改 `content`；`id`、`replacement_pattern`、`name`、`description` 等结构字段不得改动
- 本章模板**没有任何可填表格**（第 2 章无引用文档表、第 5 章无追踪表），全部内容以正文段落写入 `content`；`content` 中的换行符（`\n`）将生成独立段落
- 第 3/4 章为"原型标题改名＋逐段替换"机制：`3.1`/`4.1`/`4.1.1` 等 placeholder 的 `content` 是新标题文本，**编号（如 `3.1`、`4.1.1.7`）已按模板位置固化，改名时保留编号、只改名称**，且名称以中文开头；其余 placeholder 的 `content` 为该 guidance 段的正文

### 处理规则

1. 模板只带一组 3.X（测试准备）与 4.X/4.X.Y（测试说明）原型，本技能就地填写**一个测试项**（3.1/4.1）与**一个测试用例**（4.1.1）；更多测试项/用例请在 Word 中复制 3.1/4.1 整节扩写、编号顺延，并同步更新 4.1 引言中的用例数与第 5 章追踪
2. 第 3、4 章的引言段（"本章应分为以下几条。适用时应包括用……"）在模板中两章逐字重复，引擎无法唯一定位，**保持模板原文不替换**（此为模板固有限制，勿试图改写引擎放宽）
3. 本模板不支持动态章节（`subsections` 机制）；填写第 3/4 章时不要把 placeholder 改成 `subsections` 结构
4. 无实质内容可写的子条（如某项先决条件不适用），在对应 `content` 如实写"无"或说明，不留空（引擎拒绝空 content）
5. 需求标识、SRS 章节号、测试/用例标识必须与测试依据文档一致并在第 4、5 章间闭环

# 运行

安装依赖（首次）：

```bash
pip install -r scripts/requirements.txt
```

生成文档（推荐，使用命令行入口）：

```bash
python scripts/main.py \
  --template "documents/[16]软件测试说明-438C.docx" \
  --config "templates/config.json" \
  --project "templates/project.json" \
  --output "output/[16]软件测试说明-438C-filled.docx"
```

或使用免参数入口（**不推荐**：需先将 config.json 和 project.json 复制到 scripts/ 目录，会污染技能仓库；常规情况请用上面的 main.py）：

```bash
cd scripts
python process.py
```

输出文档路径会打印在控制台。首次在 Word 中打开时，按提示刷新目录。
