# 句式与表达规范（[23] 软件变更报告适用）

> 生成 `content` 时必须遵守以下规则；写完后逐条自查。

## 1. 陈述句式（强制）

- 变更报告以客观陈述为主：现状、理由、方案、影响用陈述句描述，主语明确（"现行软件""新软件""本次更动"等），一条只表达一个事项。
- 描述**新软件或修改后软件的行为要求**时，用"**应**""**应能**"表述，不用"必须""要""应该"混用，更不得用"希望""尽量""可能""可以考虑"。
- 不对外部实体提要求：外部系统、用户组织等的特性作为假设或事实陈述（"当……时，软件……"），禁止写成"外部系统应……"。

## 2. 量化要求（强制）

- 性能类描述必须给数值＋单位：响应时间（s/ms）、吞吐率（条/s、MB/s）、容量（条、MB）、任务数（个）、利用率（%）。
- 性能指标必须给出测量条件（如"处理 10000 行源代码时""连续运行 24 h 时"）。
- 质量属性和恢复类指标必须定量（如"调度时序误差不超过调度周期的 5%""200 ms 内恢复调度服务"），不得只写"可靠性高"。
- 数值范围写"0～99"式闭区间并注明单位；百分比写"不超过 80%"，不写"小于 80% 左右"。

## 3. 如实陈述原则（强制）

- 某节确实无内容时，写"无……"或"本节不涉及"，**禁止编造**内容凑数，也禁止留空。
- 不需要多种状态和方式、没有考虑过的备选更动等情况，直接如实说明，不得人为编造。
- 4.4「考虑但未纳入的更动」：确曾考虑过的才列入，不得为凑数编造"考虑过"的内容。
- 第 3 章只陈述现行软件事实，不得混入改进建议（改进内容属第 4、5 章）。

## 4. 编号与列举格式

- 条内列举用 a. b. c.、1. 2. 3. 编号，同层编号样式一致；替换模板中带" a. "" b. "前缀的段落时，新内容保留对应前缀。
- 交叉引用写"见 4.1""见 4.2"，章节号与 JSON 中的 `id` 一致。
- 文档名称用书名号《》，首次出现给出编号和版本。

## 5. 禁用表达

- 口语化："东西""搞""大概""差不多""之类的""等等"。
- 营销化："世界领先""极大地""完美"。
- 模糊限定："一般情况下""尽可能""较快"。若确需描述例外条件，写明条件本身（"在……条件下"）。
- 英文缩写首次出现不解释；正文术语与 `references/terminology.md` 不一致。

## 6. 一致性

- 软件名称、缩写、版本号全文一致，且与 `config.json` 封面信息一致（现行版本与新版本号要区分：第 3 章用现行版本，第 5 章起用新版本）。
- 同一概念全文同一称呼（如统一叫"抢占式调度"，不得与"抢占调度""抢占式任务调度"混用）。
- 第 4 章列出的更动条目须与第 5 章方案、第 7 章影响分析呼应，不得前后矛盾。
