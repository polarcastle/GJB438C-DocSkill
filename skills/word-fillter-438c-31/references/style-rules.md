# 句式与表达规范（[31] 软件配置管理报告 适用）

> 生成 `content` 时必须遵守以下规则；写完后逐条自查。

## 1. 陈述句式（强制）

- 配置管理报告是对已发生事实的客观记录，一律用陈述句（"……为……""报告期内共……"），不用"应""必须"等需求句式，不用"希望""尽量""可能""可以考虑"。
- 每条记录是完整陈述句，主语明确（"项目""配置管理组""报告期内"等），一条只记录一项事实。
- 评价性结论必须有数据支撑：不写"进展顺利"，写"均按计划实施，共完成配置审核2次"。

## 2. 量化要求（强制）

- 数量类记录必须给数值＋单位：配置项个数（个）、变更申请单份数（份）、工作量（人时）、备份频次（每日/每周）、不合格项数量（项）。
- 第 3 章综述、第 7 章变更、第 13 章测量的统计数字必须相互一致：变更申请总数＝批准数＋拒绝数；入库/出库单份数与第 9/10 章条数一致；工作量与综述一致。
- 日期格式全文统一（YYYY-MM-DD 或 YYYY年M月D日），单号格式统一（如 BG-2025-001）。
- 版本号格式统一（如 V1.0），与封面"版次"及 1.1 节标识一致。

## 3. 如实陈述原则（强制）

- 报告期确实无某项活动时，写"报告期内无……"或"本条不涉及"，**禁止编造**记录凑数，也禁止留空。
- 未建立的基线、未发生的审核如实说明计划安排，不得虚构。
- 人员姓名无用户提供时，用"张××"式脱敏写法或角色称谓（"配置管理组长"），不得虚构具体单位名称。

## 4. 编号与列举格式

- 条内列举用 1）2）3）分级编号，同层编号样式一致。
- 交叉引用写"见第 6 章""见 6.1"，章节号与 JSON 中的 `id` 一致。
- 文档名称用书名号《》，首次出现给出编号和版本。

## 5. 禁用表达

- 口语化："东西""搞""大概""差不多""之类的""等等"。
- 营销化："世界领先""极大地""完美"。
- 模糊限定："一般情况下""尽可能""较多"。确需描述例外条件时，写明条件本身（"在……情况下"）。
- 英文缩写首次出现不解释；正文术语与 `references/terminology.md` 不一致。

## 6. 一致性

- 软件名称、缩写、版本号、文档标识号全文一致，且与 `config.json` 封面信息一致。
- 同一概念全文同一称呼（如统一叫"配置项"，不得与"配置单元"混用）。
- 第 3 章综述中的统计数字必须与第 6～13 章明细记录一致；引用文档编号与第 2 章一致。
