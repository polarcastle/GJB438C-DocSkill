# 句式与表达规范（[26] 软件质量保证报告适用）

> 生成 `content` 时必须遵守以下规则；写完后逐条自查。

## 1. 总结报告句式（强制）

- 全文用陈述事实的书面语，动作性表述统一用"**已完成**""**均已完成**""**已归档**"等完成态，不用"将要""计划要""差不多完成了"。
- 每条措施或情况是一个完整陈述句，主语明确（"项目组""质量保证工作组""测试组"等），一条只表达一个事实。
- 职责、措施、结论分开陈述：先说做了什么（事实），再说结果（数据或结论），不混写。
- 对尚在进行或未确认的事项，写"截至本文档编制时，……"并标注"待与用户确认"，禁止写成已完成。

## 2. 量化要求（强制）

- 质量目标必须有目标值和达成值："测试覆盖率不低于95%，实测为97.6%"，不得只写"覆盖率达标"。
- 性能类指标给数值＋单位：响应时间（s/ms）、并发数（个）、连续运行时间（h）、吞吐率（条/s）。
- 评审/审核类给出次数和问题数："共提出问题5项，均已完成修改并归零"。
- 百分比写"100%""不低于95%"；时间写"2025年12月""72 h"。

## 3. 如实陈述原则（强制）

- 某条确实无内容时，写"本软件无……情况"或"本文档无……事项"，**禁止编造**活动、记录、数据凑数，也禁止留空。
- 未开展第三方测评、未发生更改、无风险项等情况，直接如实说明，不得虚构测评结论或风险。
- 单位名称、机构名称、人名缺失时，用角色称谓（"项目承担单位""具备资质的第三方测评机构"）并在收尾清单中请用户确认，**禁止编造**具体名称。

## 4. 编号与列举格式

- 条内列举用 1）2）3）分级编号，同层编号样式一致；建议每条一行（content 中换行生成独立段落）。
- 交叉引用写"见第 4 章""详见《软件配置管理报告》"，文档名称用书名号《》，首次出现给出编号和版本。
- 章节号引用与本文档实际章节一致（第 3 章质量目标和要求的完成情况、第 4 章质量管理、第 5 章项目风险监控等）。

## 5. 禁用表达

- 口语化："东西""搞""大概""差不多""之类的""等等"。
- 营销化："世界领先""极大地""完美""一流"。
- 模糊限定："一般情况下""尽可能""较好"。若确需描述例外，写明条件本身（"在……情况下"）。
- 无依据的绝对化："没有任何问题""百分之百可靠"（应写具体指标值）。

## 6. 一致性

- 软件名称、缩写、版本号全文一致，且与 `config.json` 封面信息一致（示例系统任务调度软件 / XT / V1.0）。
- 文档编号全文一致：1.1 标识、第 2 章引用文档、4.3.2 形成的文档中出现的编号应相互呼应。
- 同一概念全文同一称呼（如统一叫"质量保证工作组"，不得与"质量小组"混用；统一叫"归零"，不得与"关闭"混用）。
- 引用他文档处（《软件配置管理报告》《软件测试报告》等）须是项目实际存在的文档。
