# 句式与表达规范（[13] IDD 适用）

> 生成 `content` 时必须遵守以下规则；写完后逐条自查。

## 1. 设计说明句式（强制）

- 接口特性一律用"**应**""**应能**"表述，不用"必须""要""应该"混用，更不得用"希望""尽量""可能""可以考虑"。
- 每条特性说明是完整陈述句，主语明确（"本软件""任务调度软件""任务下发接口"等），一条只表达一个特性。
- 接口特性采用"接口/数据元素＋应＋动词＋对象＋参数/条件"结构，例如："任务下发接口应采用请求/应答方式传送任务指令。"
- 对未在本文档涵盖的接口实体，其特性一律作为假设陈述："当[未涵盖的实体]这样做时，[所指定的实体]将……"，禁止写成"上级系统应……"这类对外部实体的需求。

## 2. 量化要求（强制）

- 数据元素特性必须给：数据类型、大小和格式（长度、单位）、取值范围或枚举、准确度和精度；范围写"0～99"式闭区间并注明单位。
- 通信方法特性必须给：链接/带宽/频率/媒体、数据传送速率（数值＋单位，如"100 Mbit/s"）、周期性/非周期性及传输间隔。
- 协议特性必须给：错误控制与恢复过程（重试次数、超时时间）、同步方式（连接建立、维护、终止）。
- 容量类写"消息大小不超过 4 KB""长度不超过 2048 字节"，不写"较大""约"。

## 3. 如实陈述原则（强制）

- 某条确实无内容时，写"本接口无……特性"或"无物理兼容性要求"，**禁止编造**特性凑数，也禁止留空。
- 软件确实只有一个接口时，只建一个子条（3.2.1），如实描述，不得为填满机制而编造多个接口。
- 没有接口图时如实写"本文档以文字描述代替接口图"，不得虚构"见图 3-1"。

## 4. 编号与列举格式

- 条内列举按 a）b）c）、1）2）3）、a. b. c. 三级编号，同层编号样式一致；与模板 3.2 节原型 a）～g）组织保持一致。
- 交叉引用写"见 3.2.1""见《软件需求规格说明》3.2.1"，章节号与 JSON 中的 `id` 一致；引用的章节必须真实存在。
- 文档名称用书名号《》，首次出现给出编号和版本。

## 5. 禁用表达

- 口语化："东西""搞""大概""差不多""之类的""等等"。
- 营销化："世界领先""极大地""完美"。
- 模糊限定："一般情况下""尽可能""较快"。若确需描述例外条件，写明条件本身（"在……条件下"）。
- 英文缩写首次出现不解释；正文术语与 `references/terminology.md` 不一致。

## 6. 一致性

- 软件名称、缩写、版本号全文一致，且与 `config.json` 封面信息一致。
- 同一接口全文同一称呼、同一标识符（如统一写"任务下发接口（IF-TD-01）"，不得与"任务接收接口"混用）。
- 接口标识符编号规则全文统一（如 IF-XX-NN 两段式），数据元素、数据元素集合体编号规则同样统一。
- 第 3.1 节列出的接口必须与 3.2 节子条一一对应；第 4 章追踪的章节号、需求名称必须真实存在。
