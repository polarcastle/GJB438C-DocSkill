# [13] 软件接口设计说明（IDD）章节写作要点

> 本文件依据 `GJB438C全套模版/[13]软件接口设计说明-438C.doc` 中模板的章节说明文字提炼，逐章给出必写内容、写作深度与常见缺陷。生成任何一章的 `content` 前请先阅读本文件对应小节。

## 第 1 章 范围

### 1.1 标识
- 由引擎封面规则自动填写（文档标识号、标题、软件名称、软件缩写、软件版本号五个标识行），**不在 project.json 中配置**。
- 常见缺陷：手工在 project.json 中为 1.1 配置 placeholder（会造成锚点冲突，引擎报错）。

### 1.2 系统概述 / 1.3 文档概述
- **模板限制（重要）**：本模板这两节标题下没有任何指导段落，引擎没有可锚定的文字，**不会为这两节生成内容**。如需填写，生成后在 Word 中手工补充（1.2 写软件用途、特性、相关方、运行现场；1.3 写文档用途、内容与保密性要求）。
- 常见缺陷：误以为留空是生成失败。这是模板的固有结构，属预期行为。

## 第 2 章 引用文档

- 用表格列出：序号、名称（含编号）、版本、发布日期、来源（编写单位）。
- 常见缺陷：引用文档与正文实际引用脱节；标准名称不带编号；来源栏写"网络"等不可核查字样。
- 引擎按表头 `序号/名称/版本/发布日期/来源` 定位表格（`locator_rows` 严禁修改）；模板预置 2 个数据行，示例填 2 行，可按需增删 `rows`。

## 第 3 章 接口设计（全文核心）

### 3.1 接口标识和接口图
- 必写内容：列出本文档定义的每个接口的项目唯一标识符；用名称、编号、版本和文档引用标识接口实体（系统、配置项、用户等）；说明哪些实体接口特性固定、哪些正在开发或修改；说明接口图的使用情况（有则引用，无则如实写以文字描述代替）。
- 写作深度：概述层面，100～200 字，不展开每个接口的数据元素细节（细节属 3.2 各子条）。
- 常见缺陷：接口标识符编号规则不统一；遗漏"哪些实体特性固定/在开发"的说明；虚构接口图编号。

### 3.2 接口的项目唯一标识符（动态章节）
- 模板原型为 `3.x（接口的项目唯一标识符）`，引擎将其转换为 3.2 节标题「接口的项目唯一标识符分节」，并按 `subsections` 动态生成 3.2.1、3.2.2……每个接口一节。
- **机制约束**：`subsections` 不允许为空（空则报错）。软件确实只有一个接口时，**只建一个子条**（3.2.1），`name` 如实命名，`content` 正常描述，不得编造多个接口凑数。
- 子条 `name` 即生成的章节标题（引擎按 `name`/`content` 直接生成标题与正文），必须**以中文开头**并带项目唯一标识符，如「任务下发接口（IF-TD-01）」；子条中的 `replacement_pattern` 被引擎静默忽略，无需填写。
- 每个子条按模板原型 a）～g）组织：
  - a）接口实体分配给接口的优先级别；
  - b）要实现的接口的类型（实时数据传送、数据的存储和检索等）；
  - c）数据元素特性（9 项：名称/标识符——含项目唯一标识符、非技术名称、数据元素名称、技术名称、缩写名或同义名；数据类型；大小和格式；计量单位；取值范围或枚举；准确度和精度；优先级别/时序/频率/容量/序列等约束；保密性约束；来源和接收者）；
  - d）数据元素集合体特性（8 项：名称/标识符；数据元素及其结构；媒体及结构；视听特性；集合体间关系；约束条件；保密性约束；来源和接收者）；
  - e）通信方法特性（8 项：项目唯一标识符；通信链接/带宽/频率/媒体；消息格式化；流控制；数据传送速率及周期性；路由寻址命名约定；传输服务；安全保密考虑）；
  - f）协议特性（6 项：项目唯一标识符；优先级别/层次；打包；合法性检查/错误控制和恢复；同步；状态标识报告）；
  - g）其它特性（物理兼容性等，纯软件项目通常写"无"）。
- **关键句式**：未涵盖的接口实体特性一律用假设句式"当……时，[所指定的实体]将……"，不得对外部实体提需求；可引用数据字典、协议标准、用户接口标准代替详述。
- 常见缺陷：数据元素缺单位和取值范围；通信速率无单位；把对外部系统的要求写成"外部系统应……"；a）～g）缺一截几。
- 量化指标无源码依据时标注"待与用户确认"，不得编造数值。

## 第 4 章 需求的可追踪性

- a）从本文档中每个接口实体到相应的系统或 CSCI 需求之间的可追踪性（正向）。
- b）从影响本文档中接口的每个系统或 CSCI 需求到相应的接口实体之间的可追踪性（逆向）。
- 写作深度：逐接口列出对应的《软件需求规格说明》需求名称与章节号；章节号必须真实存在。
- 常见缺陷：只写"见《软件需求规格说明》"而不指明章节；双向追踪只写一侧；3.1 节列出的接口与追踪条目对不上。

## 第 5 章 注解

- 给出有助于理解本文档的一般信息：背景、术语表、缩略语（按字母顺序）。
- 只收录正文实际出现的术语和缩略语；术语写"中文术语（英文缩写）：中文定义"，缩略语写"缩写 - 英文全称（中文全称）"。

## 从源码到章节的映射

素材收集阶段形成的「项目画像」（开发语言、模块划分、入口、对外接口/API、关键类与函数、依赖关系）是各章内容的事实来源，按下表从用户项目源码中提取：

| 本章章节 | 从源码提取的信息 |
|----------|------------------|
| 3.1 接口标识和接口图 | 对外 API 路由/函数签名、协议与端点定义、客户端/服务端角色 |
| 3.2 各接口子条 | 请求/响应数据结构（字段名、类型、长度、取值）、通信协议与数据格式、超时/重试等配置值、带宽/速率等部署参数 |
| 第 4 章 需求的可追踪性 | 不直接取自源码：追踪到的需求条目来自《软件需求规格说明》等上游文档，章节号引用其真实编号 |
| 第 5 章 注解 | 正文实际出现的术语与缩写（源码中的协议名、格式名、框架名） |

提取规则：接口名、字段名、协议名一律沿用代码中的命名；代码中不存在的接口、字段、参数不得写入；数值类指标（长度、速率、间隔、重试次数）必须有代码或配置中的依据，确实没有时标注为待与用户确认，不得凭空给数。
