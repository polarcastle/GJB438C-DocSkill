# 句式与表达规范（[09] IRS 适用）

> 生成 `content` 时必须遵守以下规则；写完后逐条自查。

## 1. 需求句式（强制）

- 需求一律用"**应**""**应能**"表述，不用"必须""要""应该"混用，更不得用"希望""尽量""可能""可以考虑"。
- 每条需求是完整陈述句，主语明确（"本软件""任务调度软件"等），一条只表达一个要求。
- 本软件的行为需求采用"本软件应＋动词＋对象＋参数/条件"结构，例如："本软件应在 100 ms 内回复心跳响应。"
- **对外部实体用假设句式**：未涵盖实体的接口特性一律作为假定陈述，用"当[未涵盖的实体]这么做时，本软件应……"表述，禁止写成"外部系统应……""监控软件应……"。

## 2. 量化要求（强制）

- 接口量化指标必须给数值＋单位：传送速率（条/s、MB/s）、周期（ms、s）、容量（条、字节）、队列深度（个）、错误率（如"不大于 10⁻⁶"）、取值范围（"0～9999"式闭区间）。
- 资源/时限类指标给出测量条件（如"每 500 ms 周期上报一次""连续运行 24 h 时"）。
- 百分比写"不超过 80%"，不写"小于 80% 左右"；数值与单位之间留空格或不留全文统一。

## 3. 如实陈述原则（强制）

- 某接口条目确实无内容时，该项写"无"或"不适用"，**禁止编造**内容凑数，也禁止留空。
- 无物理兼容性要求、无特殊合格性方法等情况，直接如实说明，不得人为拔高。
- 接口数量以实际为准：**禁止为填满机制而编造多个接口**；实际只有一个接口时只建一个子条（见 writing-guide.md「3.1 接口标识和接口图」的机制约束）。

## 4. 编号与列举格式

- 条内列举用 a. b. c.（半角字母加点）、1) 2) 3) 编号，同层编号样式一致（与模板第 3 章原型条目保持一致）。
- 交叉引用写"见 3.2""见 3.2 c."，章节号与 JSON 中的 `id` 一致。
- 文档名称用书名号《》，首次出现给出编号和版本。

## 5. 禁用表达

- 口语化："东西""搞""大概""差不多""之类的""等等"。
- 营销化："世界领先""极大地""完美"。
- 模糊限定："一般情况下""尽可能""较快"。若确需描述例外条件，写明条件本身（"在……条件下"）。
- 英文缩写首次出现不解释；正文术语与 `references/terminology.md` 不一致。

## 6. 一致性

- 软件名称、缩写、版本号全文一致，且与 `config.json` 封面信息一致。
- 同一接口全文同一称呼（如统一叫"任务数据接口"，不得与"任务报文接口"混用）；接口的项目唯一标识符全文唯一且不变。
- 第 4、5 章引用的章节号、接口名称必须与第 3 章实际子条一致。
