# 句式与表达规范（[12] 软件详细设计说明适用）

> 生成 `content` 时必须遵守以下规则；写完后逐条自查。

## 1. 设计描述句式（强制）

- 详细设计回答"怎么做"，不是"做什么"：**不用"应""应能"提需求**（需求属于 SRS），用"本单元采用……""本单元按……方式处理……"等如实陈述句。
- 每条描述是完整陈述句，主语明确（"本单元""任务接收与解析单元"等），一条只说明一个设计点。
- 对外部实体（执行环境、外部系统等）的行为一律作为假设陈述："当外部执行环境返回状态码非零时，本单元标记任务异常"，不得写成"外部系统应……"。
- 算法和数据结构给出设计决策理由时，用"为……，本单元采用……"句式，如"为避免队头阻塞，本单元采用优先级队列而非先进先出队列"。

## 2. 量化要求（强制）

- 性能类设计指标必须给数值＋单位：响应时间（ms/s）、轮询周期（ms）、队列容量（个）、报文长度（KB）、日志保存时长（天）。
- 资源使用指标必须给出测量条件（如"处理 64 KB 报文时""监控 256 个并发任务时"）。
- 设计约束写成确定值（"就绪队列容量 1024 个任务"），不得写"较大""较快"类模糊表述。
- 数值范围写"0～99"式闭区间并注明单位；百分比写"不超过 80%"。
- 量化指标无源码或设计依据时，标注"待与用户确认"，不得凭空给数。

## 3. 如实陈述原则（强制）

- 某方面确实无内容时如实写"本单元不包含过程性命令""本单元无局部数据"等，**禁止编造**凑数，也禁止留空。
- 不需要多种设计备选、不涉及数据库、不含 GUI 等情况，直接如实说明，不得人为区分。
- 引用 DBDD、IDD 代替详述时，写明引用对象与编号。

## 4. 编号与列举格式

- 条内列举用 a）b）c）、1）2）3）、a. b. c. 三级编号，同层编号样式一致。
- 交叉引用写"见 3.1""见 3.2"，章节号与 JSON 中的 `id` 一致。
- 文档名称用书名号《》，首次出现给出编号和版本。

## 5. 禁用表达

- 口语化："东西""搞""大概""差不多""之类的""等等"。
- 营销化："世界领先""极大地""完美""业界最佳"。
- 模糊限定："一般情况下""尽可能""较快""较多"。若确需描述例外条件，写明条件本身（"在……条件下"）。
- 英文缩写首次出现不解释；正文术语与 `references/terminology.md` 不一致。

## 6. 一致性

- 软件名称、缩写、版本号全文一致，且与 `config.json` 封面信息一致。
- 同一单元全文同一称呼（如统一叫"调度决策单元"，不得与"调度模块"混用）；同一数据元素同一命名。
- 第 4 章引用的软件单元标识（SU-XX）、需求标识（R-XX）、章节号必须与第 3 章实际内容一致。
- 详细设计与概要设计、SRS 的模块划分和接口定义保持继承关系，不得矛盾。
