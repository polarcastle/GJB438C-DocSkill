# 句式与表达规范（[14] 软件可靠性和可维护性设计适用）

> 生成 `content` 时必须遵守以下规则；写完后逐条自查。

## 1. 设计策略句式（强制）

- 设计策略一律用陈述句表述："本软件……""维护者……"，不写"必须""要""应该"混用，更不得用"希望""尽量""可能""可以考虑"。
- 每条策略是完整陈述句，主语明确（"本软件""维护者""调度服务"等），一条只表达一项措施。
- 措施写法：措施＋适用对象＋可验证判据，例如："本软件对关键任务队列维护主备两份副本，主副本异常时自动切换至备副本，切换时间不超过 1 s。"
- 引用国家标准时写明标准号和名称，例如"依据 GB/T 8566""遵循 GB/T 20157-2006/ISO/IEC 14764:1999《信息技术 软件维护》"，不得篡改、简写标准号。

## 2. 量化要求（强制）

- 可靠性、可维护性指标必须给数值＋单位：切换时间（s）、恢复时间（s）、负载百分比（%）、圈复杂度（无量纲）、覆盖率（%）、MTBF（h）、MTTR（h）。
- 资源使用类指标必须给出测量条件（如"正常运行负载""峰值任务并发时""连续运行 24 h 时"）。
- 质量目标必须定量（如"分支覆盖率不低于 90%"），不得只写"可靠性高""可维护性好"。
- 百分比写"不超过 70%"，不写"小于 70% 左右"；数值范围写"0～99"式闭区间并注明单位。

## 3. 如实陈述原则（强制）

- 某条确实不采用的策略（如本软件无冗余设计、不外包维护），写明"本软件不采用……，原因是……"，**禁止编造**措施凑数，也禁止留空。
- 无源码或项目依据的数值标注"待与用户确认"，不得凭空给数；单人/离线无法确认时保留标注并列入汇总清单（见 SKILL.md「内容生成规范」收尾步骤）。
- 模板 guidance 中引用的国家标准条文保持原意，不得歪曲为项目从未实施的活动。

## 4. 编号与列举格式

- 条内列举用 a）b）c）、1）2）3）分级编号，同层编号样式一致；沿用模板列举项的破折号"—"样式。
- 交叉引用写"见 3.2""见 4.6.1～4.6.3"，章节号与 JSON 中的 `id` 一致；无锚点章节（1.2、1.3、3.9、4.6.1～4.6.3）不得假装已在本文档生成。
- 文档名称用书名号《》，首次出现给出编号和版本。

## 5. 禁用表达

- 口语化："东西""搞""大概""差不多""之类的""等等"。
- 营销化："世界领先""极大地""完美""国际先进"。
- 模糊限定："一般情况下""尽可能""较快""较高"。若确需描述例外条件，写明条件本身（"在……条件下"）。
- 英文缩写首次出现不解释；正文术语与 `references/terminology.md` 不一致。

## 6. 一致性

- 软件名称、缩写、版本号全文一致，且与 `config.json` 封面信息一致（XT-任务调度软件 / XT / V1.0）。
- 同一概念全文同一称呼（如统一叫"任务队列"，不得与"作业队列"混用）。
- 第 3 章可靠性策略与第 4 章可维护性策略不得相互矛盾（如 3.2 声明双机热备，则 4.6.2 环境资源应体现备机环境）。
