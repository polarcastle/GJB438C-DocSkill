# 句式与表达规范（[27] 软件标准化工作报告适用）

> 生成 `content` 时必须遵守以下规则；写完后逐条自查。

## 1. 工作陈述句式（强制）

- 工作报告陈述**已完成的工作**，用过去时态或完成态："开展了""完成了""形成了""通过了""编制了"，不用需求句式"应……"（"应"仅出现在引用标准条款原文时）。
- 每条陈述是完整陈述句，主语明确（"项目组""课题组""标准化工作小组"等），一条只表达一项工作。
- 行为描述采用"主语＋开展/完成/编制＋对象＋依据/结果"结构，例如："项目组按《软件标准化大纲》完成了各阶段标准化审查，共提出并关闭 5 项规范类问题。"
- 审查发现的问题必须写明"提出—关闭"的闭环结果，不得只写"发现若干问题"。

## 2. 量化要求（强制）

- 可核查的工作量必须给数值：审查次数、提出并关闭的问题数、走查覆盖的部件数、文档齐套数、检查单检查项数。
- 数值给出统计口径（如"代码走查覆盖全部软件部件""共提出并关闭 3 项描述不一致问题"）。
- 不写无法核查的虚数；"多次""大量""基本"等表述仅在无量化依据且如实说明时使用，并优先标注"待与用户确认"。
- 百分比、覆盖率写"覆盖 100%""错误率不超过 0.1%"式，注明统计对象。

## 3. 如实陈述原则（强制）

- 某章、某条确实无内容时，写"本课题未形成……"或"本条不涉及"，**禁止编造**工作成果凑数，也禁止留空。
- 阶段划分与项目实际研制过程一致：没有的阶段不建子条、不编造活动。
- 引用的标准编号、文档名称、阶段名称必须与素材收集阶段核实的事实一致。

## 4. 编号与列举格式

- 条内列举用 a）b）c）、1）2）3）、a. b. c. 三级编号，同层编号样式一致。
- 交叉引用写"见 5.1""见 6.4"，章节号与 JSON 中的 `id` 一致。
- 文档名称用书名号《》，首次出现给出编号和版本。

## 5. 禁用表达

- 口语化："东西""搞""大概""差不多""之类的""等等"。
- 营销化："世界领先""极大地""完美""一流"。
- 模糊限定："一般情况下""尽可能""较好"。若确需描述例外，写明条件本身（"在……条件下"）。
- 英文缩写首次出现不解释；正文术语与 `references/terminology.md` 不一致。

## 6. 一致性

- 软件名称、缩写、版本号全文一致，且与 `config.json` 封面信息一致。
- 同一概念全文同一称呼（如统一叫"标准化审查"，不得与"标准化检查"混用）。
- 第 5 章各阶段陈述的工作，须与第 3 章概述、第 7 章执行结果总体情况相互呼应，不得前后矛盾。
- 单位名称一律由用户提供，正文不得出现示例单位名或编造的单位名。
