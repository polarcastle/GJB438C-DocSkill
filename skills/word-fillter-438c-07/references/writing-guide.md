# [07] 软件安全性大纲章节写作要点

> 本文件依据 `GJB438C全套模版/[07]安全性大纲-438C.doc` 中模板的章节文字提炼，逐章给出必写内容、写作深度与常见缺陷。生成任何一章的 `content` 前请先阅读本文件对应小节。

## 第 1 章 范围

### 1.1 标识
- 五行标识行（文档标识号、标题、软件名称、软件缩写、软件版本号）由 `config.json` 的 document/project 字段经引擎精确规则自动填写，**不要在 project.json 中重复配置**。
- 标识号格式示例：`TN/x-DO-DS-V{N.xx}`；版本号须与封面"版次"一致。

### 1.2 系统概述（模板无锚点，生成后手工补写）
- 本模板 1.2、1.3 两节只有标题、没有任何可锚定的占位文字，引擎无法在生成时写入内容。
- 必写内容：软件用途；一般特性；开发、运行和维护的历史；需方、用户、开发方和保障机构；当前和计划的运行现场；其他有关文档。
- 写作深度：概述层面，2～3 段，不展开具体活动细节（细节属第 3、4 章）。
- 常见缺陷：把第 3 章阶段清单搬进来重复；缺少相关方和运行现场。
- **操作要求**：生成 .docx 后，在 Word 中补写这两节，并刷新目录。

### 1.3 文档概述（模板无锚点，生成后手工补写）
- 必写：本文档的用途和内容概要（大纲规定生存周期各阶段安全性要求与活动项目）；使用本文档的保密性要求（如"内部使用，不得外传"）。
- 常见缺陷：只写"本文档描述了……"一句，漏掉保密性要求。

## 第 2 章 引用文档

- 用表格列出：序号、名称（含编号）、版本、发布日期、来源（编写单位）。
- 引用文档应与正文实际引用一致：至少包括 GJB 438C 文档编制规范、软件研制任务书/合同、软件开发计划及本项目已编制的 SRS/SDD。
- 常见缺陷：标准名称不带编号；来源栏写"网络"等不可核查字样；列出正文从未引用的文档。
- "表-X"题注由引擎替换为"表2-1"，无需手工编号。

## 第 3 章 软件生存周期

### 3.1 软件生存周期各阶段对安全性要求
- 按 8 个阶段逐条改写：可行性研究与计划、需求分析、概要设计、详细设计、实现、组装测试、确认测试、使用和维护。
- 每个子条保持"阶段名——工作内容"格式（沿用模板各条破折号句式），写明本阶段要开展的安全性工作、产出与验证要求，不照抄模板通用表述。
- 各阶段安排须与项目进度、经费目标一致；有量化处给出数值与单位。
- 常见缺陷：只复制模板原文不做项目化改写；某阶段无特殊工作时不加说明地照搬；漏写产出物（计划、报告、记录）。
- **机制说明**：本模板无 X 占位子节，3.1.1～3.1.8 为静态子条，锚点为各阶段段落的模板原文，content 整段替换；新增或删除阶段子条会触发严格模式报错，不得改动。

### 3.2 软件生存周期安全性度量方法
- 必写：各阶段应进行与安全性有关的度量；区分定性估计（风险估计、检查单评审）与定量预测和测量（响应时间测量、故障注入测试统计、故障模式影响分析）；度量方法选择视阶段和活动而定。
- 写作深度：结合项目实际给出采用的度量手段与适用阶段，100～200 字。
- 常见缺陷：只写"应进行度量"不给出方法；定性定量两类方法混用不分阶段。

## 第 4 章 软件安全性大纲要求

### 章引言（总则）
- 必写：本大纲依据合同或协议书中对软件安全性的要求编制；制定和修改按质量保证有关标准规定的程序评审和审批；实施由主管机构和项目各层次安全负责人分工负责；纳入软件开发计划并与系统管理相结合。
- 项目化补充：概述本软件的安全性工作重点（结合危险场景与关键功能，如调度异常导致的任务失控与数据丢失）。
- 常见缺陷：照搬总则不复述项目重点；编造主管机构名称（应留"待与用户确认"）。

### 4.1 考虑的主要因素
- 列表项 a）～d）（生存周期阶段、安全性目标、主要任务、拟采用的安全技术）为模板通用条目，保留不动。
- 锚点为列表末项（e 项），content 写项目特定的时间、进度、经费与资源限制：研制周期（月）、安全性经费占比、存储空间与运行时间约束、软硬件运行环境。
- 常见缺陷：数值无依据（应标注待确认）；漏写软硬件环境限制。

### 4.2 主要活动项目
- 引言段 content：总述本大纲要素的应用与任务安排（落实到责任人、进度与监督更新机制），40～100 字。

#### 4.2.1 可行性论证
- 锚点为引言段（以冒号收束），content 写本软件安全性要求的可行性论证安排；模板 a）～c）三条论证目的清单保留。
- 常见缺陷：content 未以冒号结尾，与后续清单断裂。

#### 4.2.2 需求分析阶段
- content 写安全需求分析任务组成（责任明确、初步日程表、变更修改机制），以冒号收束引出模板 a）～e）清单。

#### 4.2.3 安全运行环境分析
- 锚点为列表首项（a 项），content 替换为本软件实际的安全运行和维护方式；模板 b）～e）清单保留。
- content 为单个列表项句式，以"；"结尾。

#### 4.2.4 选定或制定规范和准则
- content 写选择/制定安全规范与准则的安排，以冒号收束引出模板 a）～c）清单。

#### 4.2.5 软件安全性分析
- content 写各开发阶段开展安全性分析并编写设计报告的安排，结合项目指出重点分析项（如安全关键功能识别、故障模式影响及危害度分析），以冒号收束引出模板 a）～i）九类分析清单。
- 常见缺陷：在 content 中重复整份清单；不结合项目指出重点。

#### 4.2.6 评审（模板标准检查单，沿用不填）
- 4.2.6.1～4.2.6.4（需求分析、概要设计、详细设计、软件测试计划评审）为行业通用评审检查单，**保留模板原文，不在 project.json 配置**。
- 若项目需增加评审点（如代码评审、安全性专项评审），在生成后的 Word 中手工增补，并同步更新目录。

#### 4.2.7 安全性事件文件和数据记录
- 锚点为引言段，content 写项目安全性事件记录的范围（覆盖的事件类型）、可追溯性要求、采集条件与应用限制。
- 锚点模板原文含节号"4.2.7　"（全角空格）为定位所需，content 用项目实际表述即可。
- 模板"应监视以下关键事项："及 a）～h）监视清单保留。

#### 4.2.8 安全培训
- content 写培训计划制定与协调要求、培训对象与分级安排，以冒号收束引出模板 a）～d）培训内容清单。

#### 4.2.9 安全保障要求
- content 写安全维护保障要求的说明与计划安排，以冒号收束引出模板 a）～h）保障因素清单。

## 从源码/项目素材到章节的映射

素材收集阶段形成的「项目画像」（开发语言、模块划分、入口、对外接口/API、关键类与函数、依赖关系）是各章内容的事实来源，按下表从用户项目源码与项目资料中提取：

| 本章章节 | 从源码/项目资料提取的信息 |
|----------|---------------------------|
| 1.2 系统概述（手工补写） | 软件用途与场景：README/项目说明、入口文件职责、依赖清单反映的定位 |
| 3.1 各阶段安全性要求 | 按项目进度计划映射各阶段安全工作；模块划分与关键功能识别（用于安全性目标分配） |
| 3.2 度量方法 | 代码中的计时/日志/断言机制、测试框架能力（可用于定量测量的手段） |
| 第 4 章总则与 4.1 | 项目计划中的周期、经费、资源约束（无依据时标注待确认） |
| 4.2.3 运行环境分析 | 部署配置、运行环境脚本、运维方式说明 |
| 4.2.5 安全性分析 | 模块间调用与依赖关系（接口分析）、共享数据（数据分析）、容错与重试机制（冗余/余量分析） |
| 4.2.7 事件文件和数据记录 | 日志框架、审计日志、错误上报机制 |
| 4.2.8 培训 | 部署运维文档、操作手册（培训对象与内容的依据） |

提取规则：模块名、接口名、函数名一律沿用代码中的命名；代码中不存在的活动、机制不得写入；数值类指标（周期、经费、比例）必须有项目资料依据，确实没有时标注为待与用户确认，不得凭空给数。

## 模板已知机制说明

- **1.2/1.3 空节**：模板原文即无内容、无可锚定占位文字，引擎不处理；生成后于 Word 中补写并刷新目录。
- **4.2.6 评审检查单**：无引言段可锚，且检查单为通用标准条款，引擎不处理，保留模板原文。
- **表-X 题注**：引擎的图表重编号只识别"表X-X/表N-X"形式，本模板题注为"表-X"，故由 project.json 第 2 章段落规则显式替换为"表2-1"。
- **文件更改记录表**：封面后的更改记录表为空表，属配置管理签署页，引擎不处理，随文档流转填写。
